## Problem Statement

受监管软件（医疗器械软件 SaMD / IEC 62304，以及 GxP 场景系统 / CSV-CSA、GAMP 5、21 CFR Part 11）
每次发版都要做验证。后端和回归测试已经有自动化，但**前端显示验证**（“打开页面 X，确认字段 Y 显示 Z”）
仍然是人工执行：manual tester 逐步截图，贴进执行记录，再逐条与预期结果核对。

这部分工作有三个问题：
1. 量大：截图加核对占专职验证团队约 50% 的工作量。
2. 易错：截错图、漏时间戳、版本对不上、预期和实际不一致，都会变成审计发现，进而触发 CAPA。
3. 重复：每个季度的小版本都要整套再来一遍。

## Demand Evidence

来自创始人亲历（一个团队，非调研）：
- 专职验证团队 5 到 8 人：2 名自动化工程师，其余是 manual tester。
- 每 3 个月一次小 release，每次都要完整验证加截图，研发周期 3 年。
- 原话：“截图+核对最繁琐无聊，也会出错，出错了会有 CAPA，倒是没有召回。”
- 截图和核对约占验证工作量的 50%；其余是写 test case、执行、开会。
- 现有自动化“没有包括前端的显示测试，主要是后端+regression 测试”。
- 引入新工具要先做工具验证，约 1 人 × 2 到 3 个月。

粗算：按 6 个 manual tester 算，前端截图和核对约等于每年 2 到 3 个 FTE。
工具验证一次性成本 2 到 3 人月，只看工具验证成本，回本约 1 到 2 个月；这个数字不含方案 B 本身的开发成本（见 Open Questions 第 10 条）。

**缺口：** 还不知道谁签字付钱，以及他的考核指标（CAPA 数？release 准时率？人头？）。见 Open Questions。

## Status Quo

- 前端：manual tester 照 Word 或 PDF 测试脚本手工操作、截图、粘贴、填实际结果、签字。
- 后端和回归：自动化工程师维护脚本，但产出物不覆盖前端显示，也不直接作为前端验证证据。
- 市面上的数字化验证平台（Kneat Gx、ValGenesis、Tricentis Tosca/Vera、Sware Res_Q、Valkit.ai）
  解决的是“无纸化流转和签字”，前端执行和截图仍主要靠人。团队是否已在用其中某个平台，尚未确认。

## Target User & Narrowest Wedge

- **使用者：** 专职验证团队里的 manual tester 和自动化工程师。
- **买方（假设，待确认）：** 验证或 QA 负责人。真正在意的是文档类 CAPA 数量和 release 是否被验证拖期。
- **第一个客户：** 创始人自己所在的团队，在一个 quarterly release 上试点。
- **最窄楔子：** 前端显示验证的“执行 + 证据 + 核对”，后端和回归不碰。

## Constraints

- AI 不得进入被验证的执行路径（否则工具验证不可行）。
- 证据不得经过任何美化或剪辑：不压缩时间、不合成光标、不缩放、不重新计时。
- 需要同时满足两套监管语境。器械侧：被测产品本身适用 IEC 62304；验证工具本身的确认适用 ISO 13485 §4.1.6/§7.5.6 和 21 CFR 820。GxP 侧：CSV/CSA + GAMP 5 + Part 11。
- 工具每次升级都要重新评估是否需要再验证，所以必须能锁定版本、可复现。
- 客户环境大概率不允许把数据发到外部 LLM：agent 写脚本这一环需要支持本地或私有部署模型，或者只发送 DOM 结构。

## Premises

1. 楔子是前端显示验证的证据自动化；后端和回归已有人做。
2. AI（agent）只负责编写和修复测试脚本；脚本经人审核后锁定版本；正式执行是确定性回放，不调用 LLM。
3. 产品是审计员能签字的执行记录（每步的预期和实际结果、原始截图、需求 ID、时间戳、系统版本、执行人、审计轨迹），视频只是附加。
4. 产品自带工具验证包（IQ/OQ 模板、确定性证明、风险评估），把客户的工具验证从 2 到 3 个月压到几周。
5. **（经第二意见修订）** 只复用 storyshot 很薄的一层：目标验证（`inspect`/`check`）、登录会话（`src/auth.mjs`）、按步骤定位的报错，以及 agent 写脚本的 MCP 闭环。
   **不复用** `compose.mjs` 的时间压缩、合成光标、缩放和字幕。如果要录像，只录原始、不剪辑的画面。
6. 第一个客户是创始人自己的团队，在一个 quarterly release 上试点。

## Cross-Model Perspective

  拿它和上季度手工版本做 QA 盲审对比。跳过电子签名、平台导出、视频、LLM、验证包和 UI。

## Approaches Considered

### Approach A: Evidence Runner（最小可行）
手写 YAML 用例 → Playwright 确定性执行 → 每步原始截图加断言 → 带 hash 的 PDF/JSON 执行记录。
工作量 S，风险低。证明“证据本身站得住”，但用例仍需手写，输出格式对 QA 来说是新的。

### Approach B: 完整平台（已选）
agent 编写用例、确定性执行、Part 11 审计轨迹和电子签名、追溯矩阵、导出到验证平台、验证包（器械侧 ISO 13485 §4.1.6/§7.5.6，GxP 侧 CSA/GAMP 5）、可选原始录像。
工作量 XL，风险高。长期形态完整，可对外销售。

### Approach C: 换填表的人，不换表
把团队现有的 Word 测试脚本转成可执行 YAML，执行后把结果原样填回现有模板，QA 的 SOP 零改动。
工作量 M，风险中。阻力最小，但绑定自家模板。

## Recommended Approach

**创始人选择 Approach B（完整平台）。** 推荐方当时建议的是 C（第一周先交付 A），理由是在受监管组织里改 SOP 阻力最大。
本文按 B 设计，但按依赖关系分里程碑施工，A 和 C 作为 B 的前两个里程碑自然包含在内。

### 关键设计决定

- **门控：** M1 和 The Assignment 的结果出来、Open Questions 第 1、2、3、5 条有答案之前，不开工 M2 及之后的任何里程碑。
- **M4 之前怎么签字：** M1 到 M3 产出的记录打印出来手写签名，或者走公司现有的电子签名系统，记录里注明签名方式。
- **发给 LLM 的内容：** authoring 阶段只使用合成测试数据，发送前剥离页面文本中的个人信息；如果做不到，就只能用私有部署的模型。
  如果团队已在用 Kneat 或 ValGenesis，M4 改成“对接对方的签名和审计轨迹”，不自建。
- **工具验证先于正式使用：** M5 试点期间，人工执行仍是记录的正本，工具结果平行跑、只做对比。
  工具在 M6 完成验证后，才能产出正式证据。
- **执行器绝不调用 LLM。** “self-healing”（目标找不到时让 AI 自动换选择器）只能在 authoring 阶段发生，
  正式执行时目标找不到就判 FAIL。这条是工具能通过验证的生命线。
- **断言是一等公民。** 每个前端显示检查都写成 `expect`，“核对”由机器完成，人只复核 FAIL 和抽样。
- **原始截图与标注截图分开存：** 原始截图一律不改动一个像素；另外生成一张带断言框的标注副本，用于阅读。两者都计算 hash，并在记录里互相引用。
- **“显示正确”不能只看 DOM：** DOM 断言之外还要检查元素可见、在视口内、没有被遮挡（用 `elementFromPoint` 检查）、文字没有被截断。
  M1 的对比要专门测试 QA 是否接受这种做法；如果 QA 要求人工逐张看截图，节省比例要重新估算。
- **FAIL 流程：** FAIL → 自动生成偏差记录（含实际值和截图）→ 修复 → 用新的执行 ID 重跑，原执行记录永久保留。
  正式执行中不允许自动重试；等待策略（超时时长、等待什么条件）写在脚本里，随脚本一起锁定。
- **时间和身份：** 时间戳来自经过 NTP 同步的服务器时钟，并记录时钟源。
  角色分为发起人（启动执行的人）、复核人和批准人；机器只是执行工具，“执行人”记录的是发起人。
- **系统版本：** 优先从被测系统的 `/version` 接口或页面读取，读不到就让发起人在启动时手工确认，并在记录里注明来源。
- **审计轨迹防篡改：** 链式 hash 加 WORM 存储（或定期把链头 hash 锚定到外部只读位置），再配合操作系统层面的权限控制。只有本地 hash 链挡不住管理员整链重写。
- **保存与隐私：** 执行记录归档为 PDF/A，保存期限遵循客户 SOP。截图默认使用测试数据，不含 PHI；
  如果必须脱敏，原图加密存储，脱敏副本另行计算 hash，并在记录里声明。
- **浏览器：** 锁定一个 Chromium 版本。是否需要覆盖其他浏览器，由被测系统声明支持的浏览器范围决定（见 Open Questions）。
- **运行时：** Node 版本锁定到具体的 LTS（例如 22.x），Playwright 和 Chromium 也锁定到精确版本。
- **确定性范围：** 保证的是“同一脚本、同一工具版本、同一被测系统状态 → 同样的步骤和判定”，
  不保证截图像素级一致（时间、动态数据会变）。验证包里要如实写明这一点。

## Open Questions

1. 谁签字付钱？他的 KPI 是什么：CAPA 数、release 准时率，还是人头？（买方未确认）
2. 团队是否已在用 Kneat、ValGenesis、Tricentis 之类的平台？如果在用，M6 导出就是必需，而不是可选。
3. QA 部门接受“机器执行 + 机器截图 + 人复核”作为前端验证证据的前提条件是什么？要写进哪份 SOP？
4. 对于器械侧（ISO 13485）和 GxP 侧（CSA）两类，是否需要两套验证包，还是一套主包加映射就够？
5. 被测系统的测试环境能否稳定复现数据状态（种子数据、固定账号）？这是确定性执行的前提。
6. agent authoring 阶段能否把页面结构发给外部 LLM？还是必须本地或私有部署模型？
7. CSA 指导原则的定稿内容和适用范围需要独立核实（本次会话未核实）。
8. 商业形态：对外销售时，是开源核心加商业合规层，还是全闭源？与 storyshot（MIT）的边界怎么划？
9. 被测系统声明支持哪些浏览器？只锁定 Chromium 是否够有代表性？
10. ROI 只基于一个团队的数据，且没有计入 B 的开发成本（XL）。对外销售前，需要至少 2 个其他团队的数据。

## Success Criteria

- M1：3 到 5 条真实用例中，机器版的文档缺陷为 0，QA 复核耗时 ≤ 手工版的 50%。
- M5：平行试点中，工具与人工的判定一致率 ≥ 99%，工具记录的文档缺陷为 0，工具路径的工时比人工低 ≥ 50%。
- M6：工具自身验证用时 ≤ 3 周（基线 2 到 3 个月）。
- QA 负责人书面同意以该工具输出作为前端验证正式证据。

## Distribution Plan

- 第一阶段：内部使用，Node CLI 加私有部署（客户内网），固定 Chromium 版本的 Docker 镜像。
- 对外阶段：私有部署安装包（Docker / 离线安装）加验证包文档；不做 SaaS 多租户（受监管客户的数据不出网）。
- CI：GitHub Actions 构建并给镜像签名；每个发布版本附带可追溯的 SBOM 和 hash，供客户做 IQ。

- storyshot 的薄层：目标验证、登录会话、报错定位、MCP 闭环。以 npm 依赖或复制少量模块的方式引入，具体方式在工程评审时定。
- 相关的过往工作：probelab（agent 生成脚本、self-healing 探针），可借鉴“AI 只在 authoring 时修复”的模式。
- 需要 QA/RA 同事参与 M4 和 M6 的合规审阅。

## The Assignment

**本周内，从上季度已执行的验证记录里挑一条真实的前端显示用例（10 到 20 步），带上它的人工执行记录，去找 QA 负责人谈 15 分钟，问两件事：**
1. “如果一台机器按这个脚本执行，每步给出原始截图、预期和实际对照、hash、时间戳和版本，由人复核签字，你需要看到什么才肯把它当正式证据？”
2. “过去一年的 CAPA 里，有几条是截图或记录类的文档缺陷？”

把答案原话记下来。这两个答案决定 M1 的输出格式和整个产品的卖点（省人力，还是零文档 CAPA）。
做完这件事之前，除了 M1，不要写任何代码；M2 及之后是否开工，取决于 Open Questions 第 1、2、3、5 条的答案。
